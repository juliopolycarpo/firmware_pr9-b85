# Minor gaps: M01-M11

> Paths under `work/` name files of the local workspace. They are not published: they hold vendor firmware bytes, tool output or machine identifiers.

These are small deviations from the datasheets or weak spots in error handling. None is expected to cause the reported loop, and none has a candidate. They are listed so they are not lost. Register references are E5 v3 Vol 2 (330784-003) and E5 v4 Vol 2 (333810-002); the bit definitions used here are identical in both. PCH references are the 8-series datasheet. Datasheet sources and hashes (`work/analysis/reverse-engineering/references/INTEL-E5-SOURCES.md`).

| ID | Board / code | Gap | Reference |
|---|---|---|---|
| M01 | Both; IioInit DMI LNKCAP write (PR9 `e8b0`, MR9A `e944`) | Always sets ASPM Support (bits 11:10) to `10b` (`btr 10; bts 11`). Vol 2 lists `10` as reserved; PCIe 3.0 defines it as L1 only. The policy matches that meaning: the DMI LNKCON ASPM field comes from IntelSetup "PCI-E ASPM (Global)" (`0x549`, IIO `+0x260`), whose IFR default is "L1 Only" (2) and which is 2 in every saved IntelSetup body. So this is a datasheet-notation mismatch, not a policy error. LNKCAP is RW-O; IioDmiInitPeim does not touch these offsets. | v3/v4 §6.2.45 lnkcap |
| M02 | Both; IioInit DMI routine (PR9 `e7f0`, MR9A `e884`) | The retrain helper stores negotiated width and speed only when Data Link Layer Active is set, but its caller then re-reads LNKSTS and overwrites both values without that check. Vol 2 says the width field can hold any value while the link is down. | v3/v4 §6.2.47 lnksts bits 13, 9:4 |
| M03 | Both; IioInit DMI LNKCON2 write | Bit 4 (Enter Compliance) is copied from IIO policy `+0x550` and bit 6 (Selectable De-emphasis, RW-O) from `+0x57C`. These are the port-0 entries of IntelSetup "Compliance Mode" and "PCI-E Port DeEmphasis" (`0x839` and `0x865`; the IIO policy is IntelSetup shifted by `0x2E9`, consistent across Link Speed, Compliance, De-emphasis and both ASPM arrays). The IFR default is Disable, and all 44 compliance entries are 0 in every saved IntelSetup body on both boards. Closed: the bit is never set on these stores. | v3/v4 §6.2.57 lnkcon2 |
| M04 | Both; IioInit root-port retrain (PR9 `9164`/`f734`, MR9A `91f8`/`f73c`) | On a 10 s timeout the helper sets and clears Link Disable (`f6a8`/`916c`), waits 200 ms each time and returns. Nothing checks or reports whether the link came back, and `784c` continues with the next speed step. | v3/v4 §6.2.46 lnkcon bits 5, 4 |
| M05 | Both; PCH SMBus PEI, DXE and SMM | A completion timeout (100,000 × 10 µs, PEI `69c`) returns EFI_TIMEOUT without setting HCTL KILL. The datasheet says KILL is how software ends a host transaction, so a stuck transaction keeps HOST_BUSY set and later calls fail until reset. | 8-series §18.2.1 HST_STS, §18.2.2 HST_CNT |
| M06 | Both; PCH SMBus pre-check (PEI `3e7`) and byte-by-byte read tail (PEI `805`–`8af`, DXE `13e6`–`149d`) | If HOST_BUSY is set, the driver clears status and returns EFI_TIMEOUT at once instead of waiting. The completion mask `8E` omits FAILED (bit 4), which is harmless only because KILL is never set. On the last byte the driver clears LAST_BYTE, clears Byte Done and goes straight to the exit, which writes `FF` to HSTS; nothing waits for INTR or for HOST_BUSY to clear. Per the datasheet, clearing Byte Done is what lets the controller finish and set INTR. A late INTR is cleared by the next pre-check, which writes the read status back. A call made before the STOP completes sees HOST_BUSY and gets a spurious EFI_TIMEOUT. Modelled from the datasheet sequence, not emulated; the I2C-read callers were not identified. | 8-series §18.2.1 bits 7, 4, 1, 0 |
| M07 | Both; PCH SMBus PEI block process call (`732`–`77b`) | Rejects the reply when write count + read count > 32, which matches the SMBus 2.0 limit, then copies the reply into the caller's buffer without checking that buffer's size. Same as the Intel reference; it depends on callers passing a 32-byte buffer. | SMBus 2.0 block write-block read process call |
| M08 | Both; PchInitDxe IOBP accessors | Unbounded IOBPS busy waits (listed in H10). The IOBP registers are not in the public 8-series datasheet, so the busy-bit meaning is from the Intel reference code. | 8-series (absent) |
| M09 | Both; IioInit `6210` handshake at `62a5` | Writes `5AC00000` to uncore offset `8705C` when offset `87058` reads `5AC0xxxx`, then waits with no timeout for `87058` to change. Neither offset is in the public Vol 2 for v3 or v4, so the counterpart is unidentified. | not in v3/v4 Vol 2 |
| M10 | Both; IioInit DMI retrain helper | Writes Retrain Link twice back to back (PR9 `e690`, `e6dc`; MR9A `e724`, `e770`). Per Vol 2 the second write does nothing once the LTSSM is in Recovery; redundant, not harmful. | v3/v4 §6.2.46 lnkcon bit 5 |
| M11 | Both; IioInit port offset `438` (PR9 `76a4`, MR9A `76ac`) | Read-modify-write clears bits 16:15 and sets bits 17, 14:12 of a per-port register that is not in the public Vol 2. Meaning and correctness cannot be checked against the datasheet. | not in v3/v4 Vol 2 |
